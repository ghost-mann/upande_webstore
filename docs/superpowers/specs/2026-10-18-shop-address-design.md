# Shop address: customers on their own address, staff on the ERP

Date: 2026-10-18
Status: draft for review

## Why

The webstore runs inside the ERP, so customers would use the store and portal at
the ERP's own address (for Mona Flowers, `mona-flowers.upande.com`). Handing that
address to customers advertises the ERP's login page and desk to anyone, and on
live today a customer login can even open `/desk`. Both worry the owner more than
anything else: **customers must never find their way into the ERP.**

A customer gateway was built and tested on 2026-10-18: a Cloudflare Worker
(`~/vscodeProjects/mona-shop-gateway`, live at
`https://mona-shop-gateway.mona-flowers.workers.dev`) that stands in front of the
ERP, lets through only the store, portal and login pages and the webstore's own
API methods, and blocks the rest. It works, but it only covers the gateway's own
address. The ERP address still serves customers, and everything about the
gateway is hard-coded in its source.

This design finishes the job. It gives the shop address a home in Webstore
Settings, has the ERP send customers there, and keeps staff on the ERP.

## Goals

1. **Two addresses, one job each.** Customers use the shop address (e.g.
   `https://shop.monaflowers.co.ke`) for the store, portal and login. Staff use
   the ERP address. *(Owner's decision.)*
2. **The ERP sends customers to the shop address.** A request on the ERP address
   for a store, product, cart, wishlist, portal or signup page gets a redirect to
   the same path and query on the shop address. A customer account that tries to
   log in on the ERP address is refused and sent to the shop's login page.
   *(Owner's decision.)*
3. **The shop address is for customers only.** A staff account (any System User,
   even one linked to a customer, e.g. `austin@upande.com`) can't log in through
   the shop address. The message reads "Staff accounts sign in on the ERP", and
   the shop never names or links the ERP address. *(Owner's decision on
   customers-only; the wording and not naming the ERP address are my calls.)*
4. **What can be a setting is a setting.** *(Owner's instruction.)* Everything
   about the shop address that changes between projects or over time lives in
   Webstore Settings, not in the gateway's code. The gateway reads those
   settings from the ERP, so a change takes effect without a redeploy.
5. **Customer-facing links use the shop address.** Links built for customers
   (in pages, redirects, password setup and reset emails, quotation and claim
   notices) point at the shop address whenever it is switched on.

## Non-goals

- **Configuring DNS from the ERP.** DNS records live with the domain's registrar
  or in Cloudflare. The settings page shows the record to add and whether the
  shop address answers, but it doesn't create the record.
- **Calling Cloudflare's API from the ERP** (attaching the custom domain,
  deploying the Worker). Deploying the gateway stays a `wrangler deploy` step.
- **A separate store database or an API-sync storefront.** Already rejected; the
  ERP stays the one source of truth.
- **Changing what staff see on the ERP.** The desk is untouched.
- **Staff hardening (2FA, lockout, IP restriction).** Separate tasks in the
  go-live sheet (T26–T29).

## Anti-goals (would make this a failure even if it "works")

- Any page on the shop address that names, links or redirects to the ERP address.
- Switching the redirect on while the shop address doesn't answer, which would
  lock every customer out. This must not be possible by accident.
- A customer, through either address, reaching `/desk`, `/app`, `/api/resource`
  or any whitelisted method that isn't on the shop's allow-list.
- A site that never touches these settings behaving any differently from today.
  Everything ships off, and other projects using upande_webstore are unaffected.

## The settings

A new **Shop Address** section in Webstore Settings, on its own tab or under
Modules, whichever fits the existing layout (builder's call). Fields:

| Field | Type | Notes |
|---|---|---|
| Shop address | Data (URL) | e.g. `https://shop.monaflowers.co.ke`. Blank = feature off. Validated: https, no path. |
| Send customers to the shop address | Check | Off by default. Can only be turned on after a successful reachability check (below) in the last 10 minutes. |
| Gateway secret | Password | Generated by a "Generate secret" button; copied into the Worker as a secret. Never shown in full after saving, except through the copy action. |
| Login attempts per minute (per visitor) | Int | Default 10. Read by the gateway. |
| Let search engines index the store | Check | Default off while testing; drives the gateway's `noindex` header. |
| Extra allowed pages | Small Text | One path pattern per line, e.g. `/about`, for a project with extra public pages. Added to the gateway's built-in allow-list; it can't remove built-in blocks. |
| Extra allowed methods | Small Text | One method per line, for another app's customer-facing methods. Same rule. |
| Status panel | HTML (read-only) | Shows the DNS record to add, the last reachability check result and time, the gateway version that last fetched settings, and a "Check now" button. |

Per-storefront overrides (the existing tri-state pattern on `Webstore`) are not
needed for v1. All storefronts share one shop address and their slugs sit under
it (`/<slug>/store`). Builder: confirm the slug routing works unchanged behind
the gateway.

## How the parts fit

```
Customer ─► shop address (Cloudflare Worker) ──► ERP
                │  adds  X-Webstore-Gateway: <secret>
                │  adds  X-Forwarded-Host: <shop host>
                │  reads /api/method/upande_webstore.api.gateway.config (cached ~60s)
                ▼
          allow-list + login throttle + link rewriting (as today)

ERP before_request (new):
  request has a valid gateway secret?  → "shop request"
      staff login attempt              → refuse ("Staff accounts sign in on the ERP")
      otherwise                        → serve as normal; get_url() = shop address
  no secret, switch on, customer path  → 302 to the same path on the shop address
  no secret, customer account login    → refuse, point to the shop login page
  anything else                        → unchanged (staff, desk, API)
```

### Gateway ↔ ERP

- **Recognising shop requests:** the gateway adds a secret header on every
  request. The ERP compares it in constant time with the Password field. No
  header, or a wrong one, means a direct request.
- **Settings endpoint:** `upande_webstore.api.gateway.config`. It is guest-callable
  but answers only when the request carries the valid secret; otherwise 404. It
  returns: shop address, switch state, throttle limit, index flag, extra
  allowed pages and methods, and the built-in method allow-list (so the list
  lives in the app, next to the methods, rather than in the Worker).
- **Caching:** the gateway caches the config for about 60 seconds. If the ERP is
  unreachable or the call fails, it keeps the last good config; if it has none,
  it falls back to the built-in defaults in its source (today's behaviour).
- **The built-in allow-list moves into the app.** One Python list of
  customer-facing methods, used by the config endpoint. A unit test fails if a
  new `@frappe.whitelist(allow_guest=True)` method appears under
  `upande_webstore.api` without being classed as customer-facing or desk-only,
  so new endpoints don't silently 404 behind the gateway.

### ERP-side redirect (`before_request`)

Applies only when the switch is on and the request is *not* a shop request.

- **Customer paths:** `/store`, `/store/*`, `/<slug>/store*`, `/cart`,
  `/wishlist`, `/<slug>/cart|wishlist`, `/portal*`, `/signup`. These get a 302
  to the same path and query on the shop address.
- **Login:** a login attempt (`/api/method/login` or `cmd=login`) by a user who
  is a Website User, or who has the Customer role and no desk role, is refused
  with "Please sign in on the shop" and a link to the shop's `/login`. Staff log
  in normally.
- **Already logged-in customers on the ERP address:** their session is logged
  out and they are redirected to the shop. *(My call: the sessions are on
  different hosts anyway, so this only catches stale sessions.)*
- `/login`, `/update-password` and `/` stay on the ERP address, for staff.

### Links and emails

- **During a shop request:** set the request's host so that `frappe.utils.get_url()`
  returns the shop address. Builder: Frappe Cloud sites may set `host_name` in
  site_config, which takes precedence over the request host. Check, and if so,
  override it for the duration of a shop request only.
- **Outside a shop request** (desk actions, background jobs): emails that go to
  customers build their links from the shop address when the switch is on. At
  minimum:
  - the portal-access password setup link (the webstore's own grant flow);
  - Frappe's password reset email for Website Users;
  - the webstore's quotation and claim notifications to customers.

  Builder: list every customer-facing link the app generates and route each one
  through a single `shop_url(path)` helper.
- **Staff-facing emails** (new web quotation notices to sales) keep ERP links.

### Status panel and the safety interlock

- **"Check now"** fetches `<shop address>/store` from the ERP server and records
  success only if the response carries a marker the gateway adds (e.g. a
  response header with the gateway version). That proves the request went
  through our gateway and not some other page.
- **The switch can't be turned on** without a successful check in the last 10
  minutes. Save is refused with a message saying why.
- **A daily scheduled check** emails the System Managers if the shop address
  stops answering while the switch is on, but does *not* switch it off
  automatically. *(My call; flipping it off silently would re-expose the ERP.)*
- **The DNS hint** shows the CNAME the domain needs, pointing at the Worker's
  custom domain. Builder: confirm the exact record Cloudflare requires for a
  Worker custom domain and phrase the hint from that.

## Gateway changes

- **Read settings from the ERP config endpoint** (above). Keep the current
  built-in rules as the fallback.
- **Send** `X-Webstore-Gateway` (from a Worker secret) and `X-Forwarded-Host`.
- **Refuse staff logins:** the login response tells the gateway the user type,
  or the ERP refuses them itself (preferred: the ERP enforces it, the gateway
  only shows the message).
- **Marker header** for the reachability check.
- **Keep the current behaviour:** default-deny, `cmd` smuggling blocks,
  `/desk`→`/portal`, header stripping, link rewriting.
- **README** with the deploy steps (`wrangler login`, `wrangler secret put
  GATEWAY_SECRET`, `wrangler deploy`, attaching the custom domain).

## Testing

- **Unit and integration tests in upande_webstore**, as the suite does today, on
  webstore-test.localhost:
  - redirect on and off;
  - shop-request detection with right, wrong and missing secrets;
  - customer vs staff login on both addresses;
  - the interlock;
  - the config endpoint refusing callers without the secret;
  - `get_url()` during a shop request;
  - each customer email's links;
  - the allow-list coverage test.
- **Gateway:** extend `check.sh` and `portalcrawl.sh`:
  - a staff login through the shop is refused;
  - a customer is redirected from the ERP address to the shop;
  - settings changes are picked up within the cache window.
- **Manual end-to-end on webstore.localhost behind `wrangler dev`, then on live
  behind the workers.dev address:** guest browse, customer login, basket →
  quotation → accept, password reset email link, and the staff refusal.

## Rollout

1. Build and test on webstore.localhost. The owner works there and deploys to
   live.
2. Deploy to live with the switch off. Nothing changes for anyone.
3. Fill in the shop address (the workers.dev address first) and the secret, and
   redeploy the gateway with the secret.
4. "Check now" → turn the switch on → run the checks.
5. Later: point `shop.monaflowers.co.ke` at the Worker, change the shop address
   setting, check, done.
